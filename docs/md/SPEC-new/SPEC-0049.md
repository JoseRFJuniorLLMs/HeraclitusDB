# SPEC-0049 — Heraclitus Production Qualification, Resilience & Supply-Chain Assurance

- **Status:** Draft / Proposed
- **Autor:** Heraclitus Core, Security & Reliability Team
- **Data:** Agosto de 2026
- **Classe:** Production Readiness / Reliability / Security / Supply Chain / Release Engineering
- **Prioridade:** P0
- **Alvo primário:** `tools/heraclitus-qualifier/`, `qa/qualification/`, `.github/workflows/`, `release/`
- **Integração:** Todo o workspace HeraclitusDB, Sentinel, Forge, Dashboard, Compliance, Raft e componentes de deployment
- **Compatibilidade:** Rust Stable
- **Princípio:** *A release só é Production-Qualified quando sobreviver a carga real, falha real, ataque real, atualização real, perda real de infraestrutura e restauração real.*

---

## 0. Decisão Arquitetural

A SPEC-0049 estabelece o processo formal de **Qualificação de Produção do HeraclitusDB**.

Nenhuma versão destinada a ambiente governamental, financeiro, militar ou de infraestrutura crítica poderá ser classificada como:

```text
Production Ready
Government Ready
Mission Critical
```

apenas porque:

```text
cargo test
```

passou.

A qualificação exige seis provas independentes:

```text
Q1  REAL LOAD
Q2  REAL FAILURE
Q3  REAL ATTACK
Q4  REAL UPGRADE
Q5  REAL NODE LOSS
Q6  REAL RESTORE
```

Além das seis provas, toda release deverá passar por controles de:

```text
Continuous Fuzzing
Dependency Analysis
SBOM
Artifact Signing
Reproducible Build
Supply-Chain Verification
CVE Governance
Air-Gapped Installation
Vulnerability Response
Red Team
Disaster Recovery
Corruption Recovery
```

O resultado não será uma declaração textual.

Será um:

```text
Heraclitus Production Qualification Report
```

criptograficamente vinculado aos binários efetivamente testados.

---

## 1. Objetivo

Transformar o conceito de `production-ready` em um contrato verificável.

Uma release qualificada deverá demonstrar:

1. desempenho sob carga realista;
2. estabilidade durante execução prolongada;
3. comportamento previsível sob saturação;
4. durabilidade após interrupção abrupta;
5. recuperação após corrupção;
6. consistência após falhas de processo;
7. continuidade após perda de nó;
8. eleição e failover corretos;
9. backup efetivamente restaurável;
10. upgrade sem perda de estado;
11. rollback controlado;
12. resistência a ataques;
13. resistência a entradas malformadas;
14. integridade da cadeia de desenvolvimento;
15. capacidade de instalação em ambiente desconectado;
16. procedimento operacional para vulnerabilidades futuras.

---

## 2. Não Objetivos

Esta SPEC NÃO pretende:

- definir novos recursos funcionais;
- substituir testes unitários;
- substituir integração contínua;
- prometer disponibilidade absoluta;
- eliminar toda possibilidade de falha;
- declarar software “invulnerável”;
- declarar performance sem hardware e workload documentados;
- transformar pentest em certificação jurídica;
- considerar um benchmark criado pelo próprio projeto como prova independente suficiente;
- esconder falhas conhecidas para atingir um selo interno.

---

```text

queries

Sentinel
```


O sistema deverá receber picos acima da média.

```text

```

```text

backpressure

latency
```

```text

```

```text

```

## 19. Soak Objectives

Monitorar:


Deve ser distinguido:


```text

```

# PARTE II — Q2: REAL FAILURE

## 21. Q2 — REAL FAILURE

### 21.1 Objetivo

Provar que o banco sobrevive a interrupções que não respeitam shutdown gracioso.

---

## 22. Process Kill Injection

Durante operações aleatórias:

```text
append
fsync
index update
checkpoint
compaction
snapshot
replication
```

executar:

```bash
kill -9 <pid>
```

---

## 23. Crash Loop

Automatizar:

```text
start
load
random sleep
kill -9
restart
verify
repeat
```

por milhares de ciclos durante qualificação.

---

## 24. Crash Invariant

Após reinício:

```text
acked events
```

MUST possuir comportamento compatível com o contrato de durabilidade declarado.

Nunca poderá ocorrer:

```text
event acknowledged as durable
+
event silently absent after restart
```

---

## 25. Power-Loss Injection

`kill -9` não equivale totalmente a perda elétrica.

Testes de storage SHOULD incluir ambiente de virtualização ou harness capaz de simular:

```text
VM hard power off
block-device interruption
write interruption
host reset
```

---

## 26. Torn Write Testing

O harness deverá simular:

```text
partial sector
partial frame
truncated segment
invalid checksum
```

---

## 27. Recovery Result

Após cada crash:

```text
restart status
log head
last valid LSN
recovered records
discarded partial frame
integrity status
```

devem ser registrados.

---

## 28. Corruption Injection

Criar:

```text
qa/qualification/corruption/
```

com mutações:

```text
flip random byte
truncate segment
replace segment block
duplicate frame
remove file
modify metadata
corrupt checksum
corrupt index
corrupt snapshot
```

---

## 29. Corruption Principle

O pior resultado possível é:

```text
corruption exists
+
system silently accepts it
```

Em caso de corrupção detectável, o comportamento correto é:

```text
DETECT
ISOLATE
REPORT
RECOVER OR FAIL CLOSED
```

---

## 30. Corruption Classes

```rust
pub enum CorruptionClass {
    LogTail,
    HistoricalLog,
    DerivedIndex,
    Snapshot,
    Metadata,
    ComplianceReceipt,
}
```

---

## 31. Derived-State Recovery

Se um índice derivado for corrompido:

```text
index
  ↓
discard
  ↓
replay canonical log
  ↓
rebuild
```

SHOULD produzir estado equivalente.

---

## 32. Canonical Log Corruption

Corrupção da fonte canônica deverá:

```text
stop unsafe progression
identify affected range
report integrity failure
attempt recovery from replica/backup
```

Nunca reconstruir silenciosamente evidência inexistente.

# PARTE IV — Q4: REAL UPGRADE

## 42. Q4 — REAL UPGRADE

### 42.1 Objetivo

Provar que atualizar o banco não destrói o banco.

---

## 43. Upgrade Matrix

Cada versão deverá testar:

```text
N-1 → N
```

e, quando suportado:

```text
N-2 → N
```

---

## 44. Rolling Upgrade

Cluster deve ser testado:

```text
node A old
node B old
node C old

↓

node A new
node B old
node C old

↓

node A new
node B new
node C old

↓

all new
```

se o protocolo declarar compatibilidade rolling.

---

## 45. Mixed-Version Gate

Durante uma janela suportada:

```text
protocol mismatch
data corruption
split brain
invalid replication
```

MUST NOT ocorrer.

---

## 46. Format Compatibility

Para cada alteração persistente:

```text
WAL
snapshot
canonical model
index
network protocol
```

deverá existir teste explícito de compatibilidade.

---

## 47. Rollback

Quando rollback for suportado:

```text
N
 ↓
N+1
 ↓
failure
 ↓
N
```

MUST preservar os dados compatíveis.

---

## 48. Irreversible Migration

Se uma migração não permitir rollback:

```text
rollback_supported = false
```

deverá estar explícito antes da instalação.

A atualização exige:

```text
validated backup
restore test
operator acknowledgement
```

---

## 49. Upgrade Failure Injection

Interromper atualização em:

```text
10%
25%
50%
75%
90%
```

e testar recuperação.

---

# PARTE V — Q5: REAL NODE LOSS

## 50. Q5 — REAL NODE LOSS

### 50.1 Objetivo

Demonstrar continuidade do cluster quando infraestrutura desaparece.

---

## 51. Raft Failure Matrix

Testar:

```text
leader process crash
leader host loss
follower process crash
follower host loss
network partition
temporary packet loss
latency spike
node restart
disk stall
node permanently removed
```

---

## 52. Leader Loss

Durante escrita ativa:

```text
leader disappears
```

medir:

```text
time to elect
write interruption
client retry behavior
committed LSN integrity
duplicate events
lost acknowledged events
```

---

## 53. Split Brain Gate

Sob nenhuma circunstância:

```text
two independent leaders
+
conflicting committed histories
```

poderão ser aceitos.

---

## 54. Network Partition Testing

Topologias mínimas:

```text
1 | 2
2 | 1
leader isolated
minority isolated
majority isolated from clients
asymmetric partition
```

---

## 55. Quorum Loss

Quando quorum é perdido:

```text
unsafe writes
```

MUST NOT ser aceitas como comprometidas.

Fail closed é preferível a corrupção.

---

## 56. Node Replacement

Cenário:

```text
node destroyed
new machine provisioned
join cluster
catch-up
validation
```

deve ser testado.

---

## 57. Sentinel External Actions During Failover

A mudança de líder NÃO pode resultar em:

```text
RevokeSession x2
BlockIp x2
QuarantineHost x2
```

A idempotência definida na SPEC-0045 MUST ser validada sob failover.

# PARTE XVII — INVARIANTES FINAIS

## 144. Invariantes Finais

```text
PQ1  "cargo test passou" não significa Production Ready.

PQ2  Nenhum dado reconhecido como durável pode desaparecer silenciosamente.

PQ3  Corrupção nunca pode ser aceita silenciosamente.

PQ4  Derived state deve ser reconstruível quando a fonte canônica permanecer íntegra.

PQ5  Perda de líder não pode produzir histórico divergente.

PQ6  Retry após failover não pode duplicar efeitos externos.

PQ7  Backup só é válido depois de restore testado.

PQ8  RPO e RTO devem ser medidos, não imaginados.

PQ9  Upgrade deve ser testado sobre dados reais da versão anterior.

PQ10 Migração irreversível deve ser declarada antes da execução.

PQ11 Toda release oficial possui SBOM.

PQ12 Todo artefato oficial possui digest e assinatura.

PQ13 Toda release é vinculada a um commit específico.

PQ14 Vulnerabilidade corrigida gera regressão quando tecnicamente possível.

PQ15 Air-gap não pode realizar egress silencioso.

PQ16 Um benchmark sem ambiente documentado é inválido.

PQ17 Um teste inconclusivo não equivale a PASS.

PQ18 Uma release alterada depois da qualificação perde aquela qualificação.

PQ19 Findings bloqueantes impedem GovernmentProduction.

PQ20 Falhas históricas de qualificação não são apagadas.

PQ21 Runbook não testado não é considerado procedimento validado.

PQ22 Qualificação deve ser reproduzível por terceiro.

PQ23 O relatório final deve apontar limitações conhecidas.

PQ24 Segurança, disponibilidade e recuperação são requisitos de release, não features opcionais.
```

# PARTE XVIII — RESULTADO ESTRATÉGICO

## 145. Resultado Estratégico

A SPEC-0049 transforma a pergunta:

```text
"O HeraclitusDB está pronto para produção?"
```

em uma pergunta objetivamente verificável:

```text
"Qual release?"

"Qual digest?"

"Qual nível de qualificação?"

"Em qual hardware?"

"Com qual workload?"

"Quantas horas de soak?"

"Quantos crashes?"

"Qual resultado de failover?"

"Qual RPO medido?"

"Qual RTO medido?"

"Qual relatório de red team?"

"Qual SBOM?"

"Qual resultado do restore?"

"Qual assinatura corresponde ao binário?"
```

O objetivo final é que uma versão governamental do Heraclitus possa ser entregue acompanhada não apenas de software, mas de um **dossiê técnico verificável de confiabilidade**:

```text
              HERACLITUS SOURCE
                     │
                     ▼
                   BUILD
                     │
                     ▼
                QUALIFICATION
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
     LOAD          FAILURE       ATTACK
       │             │             │
       └─────────────┼─────────────┘
                     ▼
                  UPGRADE
                     │
                     ▼
                 NODE LOSS
                     │
                     ▼
                  RESTORE
                     │
                     ▼
             SUPPLY-CHAIN PROOF
                     │
                     ▼
               SIGNED RELEASE
                     │
                     ▼
            GOVERNMENT PRODUCTION
```

O HeraclitusDB deixa, então, de afirmar:

> **“o sistema foi projetado para ser resiliente.”**

E passa a poder demonstrar:

> **“este exato binário, identificado por este digest, foi submetido a estas falhas, nestas condições, produziu estes resultados e passou nestes critérios.”**

Esse é o nível de evidência esperado para uma plataforma que pretenda operar como infraestrutura crítica de SOC em ambientes governamentais.
