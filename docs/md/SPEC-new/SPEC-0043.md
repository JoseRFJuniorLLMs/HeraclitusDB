Fiz a consolidação. E tem uma diferença importante entre a sua auditoria e o que encontrei no código atual: **parte da infraestrutura já existe**, mas ainda não está explorada até o fim.

O `hume-kernel`, por exemplo, **já tem `AlignedBuffer` de 64 bytes** e `Vector` contíguo. Então não faz sentido criar outro mecanismo de alinhamento. O que falta é colocar **kernels SIMD reais em cima dele**.   A SPEC-0041 até descreve `simd/avx2.rs`, `avx512.rs` e `neon.rs`, mas esses módulos ainda não aparecem na árvore atual de `hume-kernel/src`.

Outro detalhe relevante: eu **não colocaria `std::simd` como requisito de produção agora**. Em agosto de 2026 o Portable SIMD de `std::simd` continua marcado como experimental/nightly; por outro lado, os intrinsics específicos de arquitetura em `core::arch`, como AVX/FMA em x86-64 e NEON/FMA em AArch64, estão disponíveis. Então a arquitetura correta para stable Rust é `scalar fallback + AVX2/FMA + AVX-512 + NEON`, com dispatch em runtime. ([Documentação do Rust][1])

O ponto mais interessante da auditoria, porém, nem é SIMD. O HNSW atual usa IDs internos densos `u32`, mas ainda usa `HashSet<u32>` para `visited`; recalcula a métrica completa por vizinho; usa o mesmo `search_layer` com heaps até nos níveis `ef=1`; e o caminho exato GPU reconstrói um `vflat` contendo todos os vetores em **cada consulta**.   Além disso, o GPU cria buffers e faz readback do vetor inteiro de distâncias antes do ranking na CPU.

Também confirmei seus outros alvos: `hume-sketches` usa FNV-1a para bytes, SplitMix64 e `% w` no Count-Min; `activation` executa `powf` repetidamente e ordena **todos** os registros para obter top-k; o JIT do HUME atualmente gera um loop escalar por linha e ainda materializa uma máscara `u8` para depois percorrê-la novamente.

Por isso eu colocaria tudo numa **SPEC-0043**, deixando esta como camada de execução matemática de alta performance.

# SPEC-0043: Heraclitus High-Performance Mathematical Execution Layer

**Status:** Draft Normativo
**Classe:** Performance / Mathematical Execution / SIMD / GPU
**Escopo:** HeraclitusDB + HUME
**Prioridade:** P0–P2
**Princípio:** *Optimize the algorithm first, the memory second, the instructions third.*

---

## 1. Objetivo

Esta especificação define a camada de execução matemática de alta performance do HeraclitusDB.

O objetivo não é alterar a semântica matemática do banco para obter números maiores em benchmarks. O objetivo é reduzir:

* operações matemáticas redundantes;
* funções transcendentais desnecessárias;
* alocações temporárias;
* movimentação de memória;
* pointer chasing;
* hashing no hot path;
* ordenações completas quando apenas Top-K é necessário;
* transferências CPU → GPU repetidas;
* materializações intermediárias;
* execução escalar onde existe paralelismo SIMD natural.

A implementação DEVE preservar:

1. determinismo;
2. replay equivalente;
3. semântica da métrica canônica;
4. precisão configurada;
5. possibilidade de fallback escalar;
6. compatibilidade CPU sem AVX;
7. compatibilidade ARM64;
8. independência entre caminho aproximado e decisão exata.

# 5. P0 — Prepared Product-Manifold Metric

## 5.1 Problema

O cálculo atual de distância entre pontos executa repetidamente operações que são invariantes durante uma consulta.

* norma esférica;
* fatores de clamp;

* inverso de `sqrt(curvature)`;
* outras constantes da assinatura.

Em uma consulta ANN, a mesma query pode ser comparada contra centenas ou milhares de candidatos.

Essas operações não devem ser recalculadas integralmente a cada comparação.

# 7. P0 — Ranking sem `sqrt` final

Para ordenação de distâncias:

```text
D = sqrt(
    wH * dH² +
    wS * dS² +
    wE * dE²
)
```

como `sqrt(x)` é monotônica para `x >= 0`, o ranking pode utilizar:

```text
D² =
    wH * dH² +
    wS * dS² +
    wE * dE²
```

Portanto, introduzir:

```rust
metric.rank_distance(...)
```

ou:

```rust
metric.dist2(...)
```

que omite o `sqrt()` final.

O `sqrt()` somente será calculado quando a API precisar devolver a distância propriamente dita.

### Invariante

```text
sort(dist) == sort(dist²)
```

para distâncias não negativas.

Isso não autoriza remover `acos()` ou `acosh()` internos da métrica canônica.

ocupam um domínio discreto pequeno.

Criar LUT:

```rust

```

em vez de executar `powi` por registrador durante cada estimativa.

# 72. Conclusão normativa

O HeraclitusDB não tratará performance matemática como uma coleção de intrinsics isolados.

A hierarquia normativa passa a ser:

```text
1. Melhor complexidade algorítmica
2. Evitar trabalho repetido
3. Evitar alocação
4. Melhorar layout de memória
5. Reduzir movimentação de dados
6. Vetorizar
7. Paralelizar
8. Acelerar em GPU
9. Aproximar somente quando mensurável e seguro
```

Em outras palavras:

```text
O(N log K)
```

deve ser preferido a tentar tornar:

```text
O(N log N)
```

10% mais rápido com SIMD.

Um cálculo que pode ser eliminado é melhor que um cálculo vetorizado.

Um vetor que já reside na GPU é melhor que uma transferência PCIe mais rápida.

Uma norma pré-calculada é melhor que um `sqrt()` otimizado executado dez mil vezes.

E uma aproximação rápida só é uma otimização quando existe um caminho exato capaz de provar que ela não compromete o contrato do sistema.

**SPEC-0043 estabelece, portanto, a Mathematical Execution Layer do HeraclitusDB: algoritmos primeiro, memória depois, SIMD em seguida e aceleradores somente onde os números justificarem.**

### Minha priorização para ganho real

Eu começaria **antes de SQ8/PQ ou AVX-512** com seis alterações: `PreparedQuery/PreparedPoint`, `VisitedTable` por epoch, `greedy_descent` especializado, Top-K parcial, `dist²` no ranking e eliminação de clones/layout SoA. São mudanças relativamente controladas e atacam diretamente o caminho vivo do HNSW.

Depois faria **GPU residente + Top-M na própria GPU**. O benchmark atual explicitamente mede a transferência dos vetores em cada chamada e mostra que esse custo faz parte do crossover CPU/GPU; isso significa que remover a transferência repetitiva muda estruturalmente a equação, não apenas alguns ciclos.

Só então eu faria **AVX2/AVX-512/NEON + SQ8/PQ + fast transcendental**. FMA faz sentido e o Rust fornece `f32::mul_add` estável, além dos intrinsics vetoriais específicos de arquitetura. ([Documentação do Rust][2])

E há uma oportunidade especialmente boa no grafo: você já implementou `DenseEntityMap` com `u32` justamente para permitir CSR e scans amigáveis a cache/SIMD. Hoje esse ativo existe, mas a parte analítica temporal ainda trabalha pesadamente com `BTreeMap`, `BTreeSet` e `String`. Ou seja, aqui também existe uma ponte pronta faltando ser atravessada.

**Minha avaliação da SPEC:** isso é mais forte que uma “SPEC de SIMD”. Ela vira uma especificação de **execução matemática inteira**, abrangendo complexidade algorítmica, locality, SIMD, quantização e GPU sem sacrificar o princípio determinístico do Heraclitus. É o nível correto para justificar essas mudanças arquiteturais.
