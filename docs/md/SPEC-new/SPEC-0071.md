# SPEC-0071 — Forge Fabric → SOC Operational Plane

> **RFC / proposta de implementação.** Este documento não afirma que os
> componentes descritos como futuros existem. O estado implementado é limitado
> ao inventário verificável da §2, fixado nos commits indicados. Toda promoção
> de maturidade exige evidência conforme a §18.

**Status:** Draft normativo  
**Data:** 2026-09-01  
**Classe:** Security Data Fabric / SOC Operations / SOAR  
**Prioridade:** P0  
**Repositórios:** `Heraclitus-Forge` e `HeraclitusDB`  
**Refina:** SPEC-0051, SPEC-0052, SPEC-0053, SPEC-0059, SPEC-0062  
**Precede a execução de:** SPEC-0048  
**Princípio:** *O Forge observa e normaliza; o HeraclitusDB preserva e deriva;
o analista decide; o Orchestrator executa somente política aprovada.*

---

## 0. Decisão

O `Heraclitus-Forge` **já é a base da Connector Fabric**. Não será criado um
segundo `heraclitus-collector` concorrente nem outro runtime de parsing.

Esta SPEC transforma o que já existe em um plano operacional SOC completo por
meio de seis deltas:

```text
Forge Fabric existente
        │
        ├── Δ1 Security Canonical Model
        ├── Δ2 Fabric de produção + adapters tipados
        ├── Δ3 Telemetry Health / Sensor Trust
        ├── Δ4 Content Hub sobre .hcx
        ├── Δ5 Case Management event-sourced
        └── Δ6 handoff seguro para SOAR / SPEC-0048
```

Nenhum desses deltas autoriza IA no caminho de produção, execução arbitrária
de shell, mutação retroativa do log ou ação externa sem política.

---

## 1. Escopo e precedência

Esta SPEC é o plano de integração e entrega das ideias espalhadas pelas SPECs
0051, 0052, 0053, 0059 e 0062. Ela não substitui os requisitos forenses e de
segurança da SPEC-0048; apenas define as pré-condições que a SPEC-0048 deverá
consumir.

Em caso de conflito:

1. invariantes do core e do log append-only prevalecem;
2. a SPEC-0048 prevalece para aprovação, idempotência, segredos e evidência;
3. esta SPEC prevalece para a fronteira Forge ↔ HeraclitusDB e para a ordem de
   implementação dos deltas;
4. documentos 0051–0062 continuam como visão funcional, não como alegação de
   código existente.

#### Feito de um lado e por ligar do outro

O modelo canónico existe **no Forge** e não tem contrapartida no HeraclitusDB:
não há uma única referência a `heraclitus-security-event/1.0` em `crates/`
(grep vazio). O evento canónico chega como atributos planos `security_*` via
`bridge.py` e é armazenado opaco — sem tipo, sem índice, sem view do lado do
banco.

É o Δ1 por fechar, e a fronteira onde ele fecha é o HeraclitusDB, não o Forge.

#### Uma contradição por resolver entre a spec e o código

A §4.1 exige que o envelope `forge-heraclitusdb/1` continue aceite. O HEAD do
Forge subiu para `forge-heraclitusdb/2` e o `bridge.py` **rejeita** qualquer
outra versão. A spec e o código dizem coisas incompatíveis; alguém tem de
ceder, e a decisão não é técnica — é sobre compatibilidade com consumidores
existentes.

```text
Heraclitus-Forge

  buffering/checkpoint

  assinatura/verificação de .hcx

  .hdb + quarentena

HeraclitusDB
  log HRKL canônico
  índices e views reconstruíveis
  TelemetryHealthGraph derivado
  findings/incidents/cases event-sourced
  política, aprovação e auditoria

heraclitus-orchestrator (SPEC-0048)
  execução de playbooks aprovados
  adapters de AÇÃO tipados
  reconciliação e compensação

Dashboard
  visualização, authoring e aprovação
  NUNCA executa ações diretamente
```

Um adapter de **ingestão** não é um executor de **ação**. O primeiro observa; o
segundo altera um sistema externo e exige as garantias da SPEC-0048.

## 4. Δ1 — Security Canonical Model

### 4.1 Compatibilidade

`forge-heraclitusdb/1` e `operational-fact/1.0` continuam aceites. O novo
contrato entra como extensão compatível:

```text
envelope              forge-heraclitusdb/1
fact_schema            operational-fact/1.0
security_schema        heraclitus-security-event/1.0  # opcional em transição
telemetry_schema       heraclitus-telemetry-health/1.0
```

Ausência de `security_schema` identifica um fato legado; não autoriza inventar
campos canônicos durante a leitura.

### 4.2 Estrutura mínima

```rust
pub struct CanonicalSecurityEvent {
    pub schema_version: String,
    pub category: SecurityCategory,
    pub event_type: String,
    pub outcome: Option<String>,
    pub severity: u8,

    pub observed_at_micros: i64,
    pub ingested_at_micros: i64,
    pub normalized_at_micros: i64,

    pub tenant_id: String,
    pub datasource_id: String,
    pub sensor_id: String,
    pub source_sequence: Option<String>,

    pub actor: Option<EntityRef>,
    pub target: Option<EntityRef>,
    pub source: Option<EndpointRef>,
    pub destination: Option<EndpointRef>,

    pub extensions: BTreeMap<String, CanonicalValue>,
    pub provenance: NormalizationProvenance,
}
```

Categorias v1:

```text
authentication network dns http process file registry endpoint
cloud identity threat_intel vulnerability email data_access privilege
alert finding incident
```

### 4.3 Proveniência obrigatória

```rust
pub struct NormalizationProvenance {
    pub forge_source_id: String,
    pub forge_lsn: u64,
    pub source_event_id: Option<String>,
    pub raw_observation_hash: [u8; 32],
    pub connector_id: String,
    pub connector_version: String,
    pub connector_digest: [u8; 32],
    pub parser_signature: String,
    pub matched_rule: String,
    pub transformation_steps: Vec<String>,
}
```

O evento central MUST permitir chegar à evidência de borda por referência e
hash. O raw não precisa viajar ao centro: minimização de dados continua válida.
Quando a política do órgão exigir raw central, ele será uma capacidade
explícita, cifrada e separada — nunca um efeito colateral da normalização.

### 4.4 Schema e mappings

Criar um crate pequeno:

```text
heraclitus-security-schema
```

Ele contém tipos, validação, canonicalização e mappings versionados. Não contém
rede, armazenamento, IA nem parsing específico de vendor.

O `.hcx` declara:

```yaml
security_schema: heraclitus-security-event/1.0
category: authentication
mapping_version: windows-security/1.0.0
required_fields:
  - observed_at_micros
  - datasource_id
  - sensor_id
```

Campos vendor-specific permanecem em `extensions`, com namespace explícito.

## 5. Δ2 — Fabric de produção

### 5.1 Um supervisor, muitos adapters

O binário `fabric` deixa de ser apenas demo e passa a supervisionar instâncias
de adapters tipados:

```rust
pub trait SourceAdapter {
    fn identity(&self) -> DatasourceIdentity;
    fn capabilities(&self) -> SourceCapabilities;
    fn poll(&mut self, limit: usize) -> Result<ObservationBatch, AdapterError>;
    fn checkpoint(&mut self, ack: SourceAck) -> Result<(), AdapterError>;
    fn health(&self) -> SourceHealthSample;
}
```

Não existe carregamento de DLL arbitrária, Python em produção ou script vindo
do pacote. Adapters v1 são implementações compiladas no binário e configuradas
pelo `.hcx`.

### 5.2 Adapters P0

Ordem mínima, ajustável ao órgão-alvo:

1. `file-tail` — extrair do `ingest` existente;
2. `syslog-udp` e `syslog-tcp` — extrair do `probe`;
3. `syslog-tls` com mTLS opcional;
4. `http-webhook` — extrair do `gateway`;
5. Windows Event Log por API nativa;
6. journald;
7. auditd.

Entra ID, Defender, Kafka, clouds e TAXII entram depois do contrato de
credenciais, paginação e rate-limit estar provado nos adapters P0.

### 5.3 Desired state e observed state

```rust
pub struct DatasourceSpec {
    pub datasource_id: String,
    pub tenant_id: String,
    pub adapter_kind: String,
    pub connector_ref: ContentRef,
    pub credential_ref: Option<SecretRef>,
    pub expected_cadence_secs: Option<u64>,
    pub max_lateness_secs: u64,
    pub buffer_limit_bytes: u64,
    pub enabled: bool,
}

pub struct DatasourceStatus {
    pub generation: u64,
    pub state: DatasourceState,
    pub last_observed_at: Option<i64>,
    pub last_ingested_at: Option<i64>,
    pub last_checkpoint: Option<String>,
    pub active_connector_digest: [u8; 32],
    pub counters: SourceCounters,
    pub last_error_code: Option<String>,
}
```

Estados:

```text
Starting Healthy Delayed Silent Drifted Degraded Quarantined Stopped
```

### 5.4 Semântica de entrega

- checkpoint só avança depois da persistência no `.hdb`;
- bridge só avança depois do ACK idempotente do HeraclitusDB;
- restart pode repetir, nunca perder silenciosamente;
- source sequence, quando disponível, participa da idempotency key;
- buffer cheio aplica backpressure ou spill cifrado; nunca descarte invisível;
- qualquer descarte autorizado gera `TelemetryDropRecorded`.

### 5.5 Verificação do `.hcx` no runtime

Antes de carregar qualquer YAML, regex, modelo ou DAG, o runner MUST:

1. resolver a trust root configurada pelo órgão;
2. validar o manifesto canônico;
3. recomputar o digest de todos os arquivos;
4. verificar Ed25519;
5. verificar compatibilidade de schema/runtime;
6. registrar `ContentActivated` com o digest exato.

`signature.sig` lida como texto não é verificação. Falha em qualquer etapa
impede o datasource de iniciar e produz estado `Quarantined`.

## 6. Δ3 — Telemetry Health e Sensor Trust

### 6.1 Eventos, não métricas efêmeras

O Forge emite eventos assinados e versionados:

```text
SensorHeartbeat
IngestionWindowClosed
TelemetryDropRecorded
SchemaDriftObserved
ParserFailureObserved
CheckpointAdvanced
ConnectorActivated
ConnectorRejected
SensorClockSkewObserved
```

Métricas Prometheus podem existir, mas não são a fonte de verdade. O estado
auditável entra no HRKL e a view é reconstruível `AS OF LSN`.

### 6.2 Janela de ingestão

```rust
pub struct IngestionWindowClosed {
    pub tenant_id: String,
    pub datasource_id: String,
    pub sensor_id: String,
    pub window_start_micros: i64,
    pub window_end_micros: i64,
    pub received: u64,
    pub parsed: u64,
    pub normalized: u64,
    pub duplicated: u64,
    pub dropped: u64,
    pub quarantined: u64,
    pub parser_errors: u64,
    pub max_observed_lateness_millis: u64,
    pub connector_digest: [u8; 32],
}
```

### 6.3 TelemetryHealthGraph

View derivada:

```text
Tenant → Datasource → Sensor → ConnectorVersion
                   ↘ Gap / Drift / Failure / Tamper Evidence
```

Cada datasource expõe cinco dimensões separadas:

```text
Coverage      dados esperados que possuem parser/conector aprovado
Freshness     atraso entre observação e ingestão
Completeness  sequência/janelas recebidas sem gaps conhecidos
Integrity     assinatura, cadeia, checkpoint e tamper
Trust         combinação versionada das dimensões anteriores
```

Não reduzir as cinco dimensões a um número sem preservar os componentes e a
versão da fórmula.

### 6.4 Regra anti-cegueira

```text
zero eventos + sensor saudável + janela sem eventos esperados = Quiet
zero eventos + heartbeat ausente ou cadência violada          = Silent
zero ataques + datasource Silent                              ≠ ambiente seguro
```

Um gap só pode ser inferido quando existe contrato de expectativa: cadência,
sequence number, watermark ou baseline aprovado. Ausência de expectativa
produz `Unknown`, nunca `Healthy` nem `Failed`.

### 6.5 Alertas de saúde

`TelemetryHealthFinding` é separado de ataque detectado. Ele pode abrir um
caso operacional, mas não deve inflar métricas de incidente de segurança.

## 7. Δ4 — Content Hub sem duplicar o Registry

### 7.1 Unidade atômica

`.hcx` continua sendo a unidade imutável e assinada. Não será criado outro
formato executável para connectors/parsers.

O `.hcx` v2 MAY conter diretórios opcionais:

```text
manifest.yaml
architecture.yaml
ontology.yaml
reasoning.yaml
behavior.model
normalization/
detections/
hunts/
dashboards/
playbooks/
mitre/
docs/
tests/
sbom/
signature.sig
```

### 7.2 Security Pack

`.hrkp` pode existir apenas como **agregado de distribuição**, nunca como um
segundo runtime format:

```text
pack-manifest.json
content/                    # zero ou mais .hcx imutáveis
dependencies.lock
sbom/bom.cdx.json
SHA256SUMS
signature.sig
```

O pack referencia cada `.hcx` por ID, versão e digest. Instalar um pack equivale
a instalar unidades `.hcx` verificadas individualmente e depois ativá-las por
política.

### 7.3 Lifecycle

```text
Draft → Validated → Signed → Published → Staged → Active → Deprecated → Revoked
```

Publicação e ativação são atos diferentes. Um pacote assinado pode estar
publicado e ainda não autorizado num tenant.

### 7.4 Modos de distribuição

- registry local Git/filesystem;
- mirror HTTPS autenticado;
- bundle air-gap assinado;
- catálogo online opcional.

O modo air-gap MUST permitir verificar pacote, dependências, SBOM e trust root
sem DNS, NTP ou acesso ao fornecedor.

### 7.5 Rollout

Suportar:

```text
validate-only
shadow
canary por datasource
activate
rollback para digest anterior
revoke
```

Rollback cria novo evento de ativação; não apaga o histórico.

## 8. Δ5 — Case Management event-sourced

### 8.1 Modelo

```text
Finding → FindingGroup → Investigation → Incident → Case
```

Sentinel pode produzir Finding/Incident. Case é a unidade humana de trabalho e
não deve ser inferida silenciosamente por um modelo.

### 8.2 Eventos mínimos

```text
CaseOpened
CaseTitleChanged
CasePriorityChanged
CaseOwnerAssigned
CaseWatcherAdded
CaseTaskCreated
CaseTaskCompleted
CaseNoteAdded
CaseNoteRevised
EvidenceBookmarked
IncidentLinked
IncidentUnlinked
CaseEscalated
CaseStatusChanged
CaseMerged
CaseSplit
CaseClosed
CaseReopened
```

O estado é uma view derivada. Não existe `UPDATE case SET ...` como fonte de
verdade.

### 8.3 Concorrência e idempotência

Todo comando de caso carrega:

```text
command_id
case_id
expected_revision
principal
reason
```

`expected_revision` divergente gera conflito explícito. Retry do mesmo
`command_id` retorna o resultado original.

### 8.4 SLA

Deadlines são eventos versionados e derivados da política vigente quando o caso
é criado. Alterar a policy não reescreve prazos históricos.

```text
triage_due
investigation_due
containment_due
review_due
regulatory_due
```

### 8.5 Separação de tipos

Notas e relatórios MUST distinguem:

```text
RawEvidence
NormalizedEvent
DerivedDetection
ModelHypothesis
AnalystConclusion
ExternalEvidence
```

## 9. Δ6 — Handoff para SOAR / SPEC-0048

SOAR só começa depois de existir:

- Case/Incident com identidade e revisão estáveis;
- evidência referenciada por LSN/hash;
- PolicyDecision persistida;
- principal autenticado e RBAC;
- Content Hub capaz de ativar playbook assinado;
- health gate da telemetria.

### 9.1 Health gate

Uma ação automática de alto impacto MUST ser recusada ou exigir aprovação
reforçada quando a telemetria requerida estiver `Silent`, `Unknown` ou abaixo
do trust mínimo declarado pelo playbook.

```yaml
required_telemetry:
  - datasource_class: identity
    minimum_trust: 0.90
    maximum_age_secs: 300
```

### 9.2 Playbook como conteúdo

O Forge pode authorar e simular Playbook IR. O `.hcx`/`.hrkp` pode distribuí-lo.
Somente `heraclitus-orchestrator` o executa depois de assinatura, ativação,
policy e aprovação.

### 9.3 Invariantes herdados da SPEC-0048

- nada de arbitrary shell por default;
- segredo nunca chega à UI, ao LLM ou ao pacote;
- execução externa é at-least-once + idempotência + reconciliação;
- `UNKNOWN` não é convertido em `FAILED` automaticamente;
- ações críticas exigem human-in-the-loop configurável;
- toda tentativa, inclusive recusada, é auditada;
- somente o líder vigente pode executar em cluster.

## 10. Superfícies de API

APIs são separadas por autoridade:

```text
Ingest API        writer de telemetria
Content API       publisher/content-admin
Health API        reader/auditor
Case API          analyst/case-manager
Approval API      security-approver
Orchestrator API  executor interno
```

Operações administrativas não compartilham token com o writer do Forge.

Endpoints mínimos conceituais:

```text
POST /v1/telemetry/windows
GET  /v1/datasources
GET  /v1/datasources/{id}/health
POST /v1/content/validate
POST /v1/content/activate
POST /v1/cases
POST /v1/cases/{id}/commands
GET  /v1/cases/{id}?as_of_lsn=N
POST /v1/playbook-runs/{id}/approvals
```

REST é uma projeção conveniente. O contrato principal deve existir em protobuf
versionado e reservar field numbers removidos.

## 11. Multi-tenancy, identidade e segredos

- `tenant_id`, `datasource_id` e `sensor_id` são obrigatórios e não derivados
  de conteúdo livre;
- identidade do titular LGPD continua separada da identidade do produtor;
- trust roots do Content Hub são configuradas por órgão/tenant;
- `registry/publisher.pub` do repositório serve a desenvolvimento e fixtures,
  não é confiança universal embutida;
- credenciais aparecem somente como `secret://...`;
- logs, status, quarentena e relatórios não imprimem segredo nem raw sensível;
- cada adapter declara capabilities e egress esperado;
- StrictAirGap recusa adapters que precisam de rede externa.

## 12. Falhas e operação degradada

| Falha | Comportamento obrigatório |
|---|---|
| assinatura `.hcx` inválida | datasource não inicia; `ConnectorRejected` |
| parser não casa | quarentena cifrada + `SchemaDriftObserved` |
| buffer cheio | backpressure/spill cifrado; descarte apenas explícito |
| bridge indisponível | continuar no `.hdb` até limite; nunca avançar ACK central |
| clock skew | marcar observação; preservar tempos original e de ingestão |
| sensor silencioso | `Silent`, não `Healthy` |
| restart | recuperar checkpoint e repetir com idempotência |
| versão incompatível | fail-closed antes do primeiro Append |
| conteúdo revogado | bloquear novas ativações; política decide instâncias ativas |
| concorrência em Case | conflito de revisão, sem last-write-wins silencioso |
| timeout de ação SOAR | `Unknown` + reconciliação |

## 13. Migração

### 13.1 Forge 1.0

1. todo fato legado continua consultável;
2. bridge passa a aceitar o bloco canônico opcional;
3. connectors são promovidos um a um para `.hcx` v2;
4. fatos novos carregam digest do connector e IDs de datasource/sensor;
5. nenhuma retro-normalização ocorre silenciosamente.

Reprocessamento histórico, quando autorizado, cria novos eventos derivados com
`derived_from` apontando aos LSNs originais e ao digest do novo connector.

### 13.2 Content Hub

O registry atual é importado sem reempacotar bytes. Um índice de catálogo novo
referencia os digests existentes. Só uma publicação futura precisa emitir
metadados v2.

## 15. Gates obrigatórios

### Fabric

| Gate | Prova |
|---|---|
| CF0 Runtime Trust | um byte alterado no `.hcx` impede load |
| CF1 No Loss | crash entre persistência/checkpoint não perde evento |
| CF2 Idempotency | retry não duplica no HeraclitusDB |
| CF3 Backpressure | destino lento não causa descarte invisível |
| CF4 Rotation | truncagem/rotação de fonte mantém continuidade declarada |
| CF5 TLS | Syslog TLS/mTLS recusa peer/config inválida |
| CF6 Isolation | segredo e raw não aparecem em log/status |

|---|---|
| CM0 Determinism | mesma observação + mesmo digest → mesmos campos canônicos |
| CM1 Provenance | todo evento volta ao Forge LSN/hash/connector |

### Telemetry Health

| Gate | Prova |
|---|---|

|---|---|

## 16. Testes adversariais mínimos

- `.hcx` assinado por chave não confiável;
- troca de `architecture.yaml` depois da assinatura;
- regex catastrófica e linha acima do limite;
- UDP flood, TCP slowloris e TLS renegotiation abuse;
- source sequence repetida, regressiva e com salto;
- relógio do sensor adiantado/atrasado;
- bridge fora durante horas e buffer no limite;
- connector canary pior que a versão ativa;
- pack com dependency confusion;
- trust root trocada sem aprovação;
- dois analistas alterando o mesmo caso;
- nota revisada tentando apagar a versão anterior;
- approval replayada contra outro action digest;
- executor que respondeu depois do timeout;
- líder antigo tentando executar após perder o lease;
- tenant A tentando ler/ativar conteúdo ou caso do tenant B.

---

## 17. Não objetivos

- reescrever o Runner em outro runtime;
- executar Python/IA no data plane;
- prometer exactly-once em sistemas externos que não o oferecem;
- copiar todo raw para o centro por omissão;
- criar marketplace público antes do registry offline funcionar;
- permitir shell genérico em playbooks;
- transformar métricas Prometheus em fonte de verdade histórica;
- declarar silêncio de sensor como ausência de ataque;
- alegar homologação universal de um connector por ele existir no registry;
- iniciar qualification longa antes de congelar o artefato de release.

## 18. Definition of Done e maturidade

Cada capability mantém cinco colunas independentes:

```text
E1 code_exists
E2 runtime_wired
E3 automated_evidence
E4 independent_qualification
E5 packaged_supported_product
```

O nível exibido é o último nível consecutivo provado. “Parcial” não promove o
nível; fica em `known_gaps`.

## 19. Ordem final

```text
0051 modelo canônico
   ↓
Forge Fabric existente + delta 0052
   ↓
0062 Telemetry Health
   ↓
0053 Content Hub sobre .hcx
   ↓
0059 Case Management
   ↓
0048 SOAR
```

O objetivo não é tornar o Heraclitus “mais banco”. É fazer o que já existe
receber fontes reais, saber quando ficou cego, distribuir conteúdo confiável,
organizar o trabalho humano e só então executar resposta automatizada.
